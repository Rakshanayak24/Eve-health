# EVE Healthcare — Diagnostic Booking & Payment Service

A backend service for browsing diagnostic centres/tests, booking a test, and paying for it
through a **simulated** payment gateway with an **idempotent** webhook. Built with **FastAPI**,
**SQLAlchemy**, and **PostgreSQL**.

- Stack: FastAPI + SQLAlchemy 2.0 + PostgreSQL + JWT (python-jose) + bcrypt (passlib)
- Tests: pytest + FastAPI `TestClient`, isolated on in-memory SQLite (no external services needed to run the suite)
- Bonus items included: Docker & docker-compose, Swagger/OpenAPI docs (built into FastAPI), structured (JSON) request logging, pagination, unit/integration tests

---

## 1. Running the project locally

### Option A — Docker (recommended, zero local setup)

```bash
docker compose up --build
```

This starts a Postgres 16 container and the API. Once the `db` service reports healthy, the API
starts and creates its tables automatically on startup.

PostgreSQL is exposed on host port `5433` by default so it can run alongside a local PostgreSQL
server using `5432`. The API connects to the database over Docker's internal network. To use a
different host port, set `POSTGRES_HOST_PORT` before starting Compose (PowerShell example:
`$env:POSTGRES_HOST_PORT=5434; docker compose up --build`).

- API: http://localhost:8000
- Interactive docs (Swagger UI): http://localhost:8000/docs
- Alternative docs (ReDoc): http://localhost:8000/redoc
- Health check: http://localhost:8000/health

### Option B — Local Python (requires a local/remote Postgres instance)

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
# edit .env -> set DATABASE_URL to point at your Postgres instance, e.g.
# DATABASE_URL=postgresql://eve_user:eve_password@localhost:5432/eve_healthcare

uvicorn app.main:app --reload
```

Requires **Python 3.10+** (the code uses `X | None` union type hints) and a reachable Postgres
database. Tables are created automatically on startup via `SQLAlchemy.metadata.create_all`
(see "What I'd improve" — a real project should use Alembic migrations instead).

### Running the tests

```bash
pip install -r requirements.txt
pytest -v
```

The test suite spins up a fresh **in-memory SQLite** database per test (see `tests/conftest.py`),
so it needs no Docker/Postgres and each test is fully isolated. 30+ tests cover auth, catalog
management, bookings, payments, authorization, and — most importantly — **webhook idempotency**
(`tests/test_webhook.py`).

## 2. API endpoints & example requests

All request/response bodies are JSON. Full interactive documentation (with a "Try it out" button)
is auto-generated by FastAPI at `/docs`.

> **Swagger UI note:** the built-in "Authorize" button expects OAuth2 form-encoded credentials.
> Since `/auth/login` accepts a plain JSON body (simpler for a JSON API), the easiest way to test
> auth in Swagger is: call `POST /auth/login` via "Try it out", copy the `access_token` from the
> response, then click "Authorize" and paste it in as `Bearer <token>`.

### Authentication

| Method | Path            | Auth | Description                    |
|--------|-----------------|------|--------------------------------|
| POST   | `/auth/signup`  | none | Create an account              |
| POST   | `/auth/login`   | none | Log in, receive a JWT          |

```bash
curl -X POST http://localhost:8000/auth/signup \
  -H "Content-Type: application/json" \
  -d '{"email": "jane@example.com", "full_name": "Jane Doe", "password": "supersecret1"}'

curl -X POST http://localhost:8000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email": "jane@example.com", "password": "supersecret1"}'
# -> {"access_token": "<JWT>", "token_type": "bearer"}
```

Use the token on every subsequent authenticated call:
`-H "Authorization: Bearer <JWT>"`

### Diagnostic centres & tests

| Method | Path                          | Auth | Description                                   |
|--------|-------------------------------|------|------------------------------------------------|
| POST   | `/centres/`                   | yes  | Create a centre (optionally with its tests)    |
| GET    | `/centres/?location=&limit=&offset=` | no | List centres, paginated, optional location filter |
| GET    | `/centres/{centre_id}`        | no   | Get one centre + its tests                      |
| POST   | `/centres/{centre_id}/tests`  | yes  | Add a test to an existing centre               |
| GET    | `/centres/{centre_id}/tests`  | no   | List a centre's tests                          |
| GET    | `/tests/{test_id}`            | no   | Get a single test                              |

```bash
curl -X POST http://localhost:8000/centres/ \
  -H "Authorization: Bearer <JWT>" -H "Content-Type: application/json" \
  -d '{
        "name": "City Diagnostics",
        "location": "Bengaluru",
        "tests": [{"name": "Complete Blood Count", "price": 500}, {"name": "Lipid Profile", "price": 800}]
      }'

curl "http://localhost:8000/centres/?location=bengaluru&limit=10&offset=0"
```

### Bookings

| Method | Path                        | Auth | Description                                |
|--------|-----------------------------|------|----------------------------------------------|
| POST   | `/bookings/`                | yes  | Book a test (status starts as `PENDING`)     |
| GET    | `/bookings/?status=&limit=&offset=` | yes | List **your own** bookings, paginated, optional status filter |
| GET    | `/bookings/{booking_id}`   | yes  | Get one of your own bookings                 |
| PATCH  | `/bookings/{booking_id}/cancel` | yes | Cancel a booking (not allowed once `CONFIRMED`) |

```bash
curl -X POST http://localhost:8000/bookings/ \
  -H "Authorization: Bearer <JWT>" -H "Content-Type: application/json" \
  -d '{"test_id": "<test-id>", "appointment_time": "2026-10-05T09:30:00"}'
```

### Payments

| Method | Path                 | Auth | Description                                                      |
|--------|----------------------|------|--------------------------------------------------------------------|
| POST   | `/payments/`         | yes  | Simulates charging the user for a booking                          |
| POST   | `/payments/webhook/` | secret header | Receives async payment-status updates from the (simulated) provider, **idempotently** |

```bash
# Pay for a booking (random SUCCESS/FAILED outcome based on PAYMENT_SUCCESS_RATE)
curl -X POST http://localhost:8000/payments/ \
  -H "Authorization: Bearer <JWT>" -H "Content-Type: application/json" \
  -d '{"booking_id": "<booking-id>"}'

# Force a deterministic outcome for testing/demoing
curl -X POST http://localhost:8000/payments/ \
  -H "Authorization: Bearer <JWT>" -H "Content-Type: application/json" \
  -d '{"booking_id": "<booking-id>", "force_status": "SUCCESS"}'

# Simulate the provider calling our webhook (note the shared-secret header)
curl -X POST http://localhost:8000/payments/webhook/ \
  -H "X-Webhook-Secret: webhook_shared_secret_demo" -H "Content-Type: application/json" \
  -d '{"event_id": "evt_123", "provider_reference": "<provider_reference-from-payment>", "status": "SUCCESS"}'
```

**Idempotency guarantee:** replaying the exact same webhook body (same `event_id`) any number of
times has no additional effect — the response reports `"duplicate": true` and the booking/payment
state is left untouched. See `app/routers/payments.py` for the full explanation and
`tests/test_webhook.py` for the tests that pin this behaviour down.

## 3. Database / schema design

```
users
 ├─ id (PK, uuid)         email (unique)      hashed_password      full_name      created_at
 │
 ├──< bookings ────────────────────────────────────────────────────────────────────────┐
 │     id (PK)  user_id (FK)  test_id (FK)  centre_id (FK)                              │
 │     appointment_time  amount  status[PENDING|CONFIRMED|FAILED|CANCELLED]              │
 │     created_at  updated_at                                                            │
 │                                                                                       │
diagnostic_centres                                                                       │
 id (PK)  name  location  created_at                                                     │
 │                                                                                        │
 └──< diagnostic_tests                                                                    │
       id (PK)  centre_id (FK)  name  price  created_at                                   │
       UNIQUE(centre_id, name)  — a centre can't list the same test name twice            │
                                                                                            │
                                                                                            ▼
                                                                                       payments
                                                                             id (PK)  booking_id (FK)
                                                                             amount  status[PENDING|SUCCESS|FAILED]
                                                                             provider_reference (unique)
                                                                             created_at  updated_at

webhook_events
 id (PK)  event_id (unique)  payment_id (FK, nullable)  payload (raw JSON snapshot)  created_at
```

Design choices:

- **`Booking` stores a copy of `amount`** (from the test's price at booking time) rather than
  always joining to `DiagnosticTest.price`. This protects historical bookings from later price
  changes at the centre.
- **`Payment` is append-only per attempt**, not a single mutable row on `Booking`. A booking can
  end up with more than one payment row (e.g., a `FAILED` attempt followed by a retried
  `SUCCESS`), which preserves a full audit trail instead of overwriting history. `provider_reference`
  is unique per attempt and is what the webhook payload references.
- **`WebhookEvent` is the idempotency ledger.** Every event we've successfully processed is
  recorded by `event_id` (`UNIQUE`). A second delivery of the same `event_id` is detected by a
  lookup, and — to also cover the race where two identical deliveries arrive concurrently — the
  column-level `UNIQUE` constraint gives us a second, DB-enforced guarantee: if two requests
  both pass the lookup and try to insert, only one `INSERT` succeeds and the loser is caught via
  `IntegrityError` and treated as a duplicate rather than an error.
- **IDs are UUID strings**, not auto-increment integers, so they're safe to expose in URLs
  without leaking sequence/volume information.
- **Enums stored as plain strings (`native_enum=False`)** rather than native Postgres `ENUM`
  types, so the same models work unmodified against SQLite in tests and Postgres in
  dev/production, and so adding a new status later doesn't require an `ALTER TYPE` migration.

## 4. Important assumptions

- **No separate "centre admin" role.** Any authenticated user can create a diagnostic centre or
  add a test to one. A real product would restrict this to a staff/admin role — flagged in
  "What I'd improve" below.
- **A booking is created directly in `PENDING`,** and `POST /payments/` resolves the payment
  synchronously (mirroring how many test/sandbox payment gateways behave) *and* still exposes
  `POST /payments/webhook/` as the channel a real, asynchronous provider would use to report the
  final outcome later — both paths update the same booking/payment state, both are idempotent
  entry points into the same `_apply_outcome` logic.
- **A `CONFIRMED` (paid) booking cannot be self-service-cancelled** via `PATCH
  /bookings/{id}/cancel` — the assumption is that a paid appointment requires a refund/support
  flow, which is out of scope here. Cancelling an already-`CANCELLED` booking is a no-op (HTTP
  200), not an error, since retries of a cancel action shouldn't be punished.
- **The webhook's authenticity is checked with a static shared-secret header**
  (`X-Webhook-Secret`), not HMAC request-signing. This is enough to demonstrate the idempotency
  requirement the assignment cares about without depending on a specific real provider's
  signature scheme.
- **A webhook that reports a different outcome for a payment that has already reached a terminal
  state (`SUCCESS`/`FAILED`) is logged and ignored, not applied** — this prevents a stale/out-of-order
  delivery from flipping an already-settled booking (see `tests/test_webhook.py::test_webhook_does_not_flip_terminal_state_from_stale_event`).
- **Tables are created via `Base.metadata.create_all`** at startup rather than Alembic
  migrations, to keep local setup to one command for this assignment's scope.
- Passwords require a minimum of 8 characters; no additional complexity rules are enforced.

## 5. What I'd improve with more time

- **Alembic migrations** instead of `create_all`, so schema evolution is explicit and reversible.
- **Role-based access control** (e.g. an `is_admin`/`centre_owner` flag or a separate roles table)
  so creating/editing centres and tests is restricted appropriately.
- **HMAC-signed webhooks** (verify a signature over the raw body with a per-provider secret)
  instead of a static shared-secret header, closer to how Stripe/Razorpay actually work.
- **Async job for payment settlement** (Celery/RQ + Redis) so `POST /payments/` returns
  immediately with `PENDING` and the webhook is the *only* path to a terminal state, which is
  more realistic than resolving synchronously.
- **Rate limiting** on `/auth/login` and `/payments/webhook/` to blunt brute-force/replay-flood
  attempts.
- **Retry/backoff handling + dead-lettering** for webhook processing failures, plus a
  reconciliation job that reconfirms payment status with the provider for bookings stuck in
  `PENDING` past a timeout.
- **Structured logging → an actual log aggregator** (the current logging is a JSON-ish
  print-formatted line to stdout, fine for local dev/containers, not a real log pipeline).
- **More granular pagination metadata** (e.g. `has_more`, cursor-based pagination for large
  result sets instead of offset-based).
- A small Postman/Insomnia collection or `httpie`-based smoke-test script for manual QA.
